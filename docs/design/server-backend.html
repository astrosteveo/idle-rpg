Server Backend Design

How an entirely client-side idle RPG grows a server without rewriting the simulation it already has.

Repo astrosteveo/idle-rpg Branch worktree-server-backend-design Status Design, with one claim proven in code

What the backend is for

Today the simulation runs in the browser, the save lives in localStorage, and nothing leaves the machine. Three goals justify changing that, in the order they pay off.

  • Your character follows you. Play on a phone at lunch and a desktop at night, same character. This is the reason most players will notice a server exists.
  • Time accrues honestly. An idle game promises the world moves while you're away. Right now that promise is kept by your own clock, which you can set to whatever you like.
  • The world is shared. Apex beasts already walk on a schedule every client agrees on. A server turns that schedule into a kill feed, ladders, and the ghosts of other players hunting the same ground.

Non-goals for the first release

  • No real-time multiplayer. No shared combat, no synchronized positions.
  • No trading. Every verification property below assumes items are generated for one character and never move. Trading turns a tolerable cheat into an economy-wide one.
  • No sign-up wall. An idle game that asks for an email before you swing a sword loses most of its players at the sign-up.

Why the live simulation stays on the client

The constraint everything else routes around

The moment-to-moment combat simulation is not replayable, and can't be made authoritative without a rewrite.

  • One RNG stream serves everything. The same sequence feeds combat damage, loot rolls, float-text offsets, corpse lean, and beast wander points. Cosmetic draws and consequential draws advance the same stream, so any difference in what got drawn changes what drops.
  • Frame timing feeds the simulation. The frame loop quantizes the real delta and passes it to update(). A 60 Hz client and a 144 Hz client take different numbers of steps, and so make different numbers of rand() calls.
  • The view rectangle reaches the simulation. Anything that varies with window size can't be reproduced from inputs alone.

Fixing that means separating cosmetic randomness from consequential randomness, moving to a fixed timestep, and removing the view from the simulation's inputs. That's a real project, and it buys a property this game doesn't need. So the server is designed never to need it.

The trust model: verify, don't simulate

The server doesn't re-run combat. It checks that the save a client hands back could have come from an honest game.

TIER 1

Exact invariants

Closed-form facts about a legal save. Any violation is proof, not a signal.

  • Items match their generator. makeItem() is nearly deterministic given base, item level, and rarity. Value and base damage are exact expressions.
  • Experience matches level. xpNext must equal xpForLevel(level), and xp must be below it.
  • Talents match level. One pick per unlocked row, never two from one row.
  • Milestones match counters. A claimed milestone's threshold must actually be met.
  • Apex kills match the clock. No stored boss window may exceed the server's current one — a tight bound on the largest single reward in the game.

Ships as a hard rejection.

TIER 2

Rate ceilings

killsPerHour() already computes how fast a build kills a species. Reuse it as a cheat oracle: derive stats from the previously stored save, compute the best rate that build could reach, multiply by elapsed wall-clock seconds, add headroom.

The ledger discounts by OFFLINE.efficiency (0.72) for healing, pathing, and respawn waits. Live play beats that, so start headroom near 3× and tune it against real data.

Ships in shadow mode. Record, don't reject.

TIER 3

The clock

The server stamps savedAt itself and ignores the client's. That one change makes the offline ledger honest, because the ledger is a pure function of elapsed time and the client no longer gets a vote on elapsed time.

One line of authority, most of the benefit.

The item check, measured

Tier 1's item check is the load-bearing claim of this design, so it exists in code rather than in prose. game/verify.ts reconstructs the loot generator's expressions, and tests/unit/verify.test.ts runs it against thousands of generated items plus a set of tampered ones.

Affix magnitudes are the only soft spot, because they're the one part the generator rolls rather than derives. A cheater's entire remaining budget is a fraction of one affix line on one item — not worth their trouble or yours. Hand-edited gear, the dominant attack on a game like this, is detectable without simulating anything.

Stack and layout

TypeScript on both sides, with the simulation shared as a package. This isn't a preference, it's a constraint: the tuning tables run to 1,551 lines, and the server's ledger has to produce the same numbers as the client's estimate, forever. Any second implementation drifts, and every drift is a payout bug. The game code is already pure TypeScript with no runtime dependencies, so lifting it costs almost nothing.

packages/
  sim/      // today's src/game and src/core, unchanged
  client/   // today's src/render, src/ui, src/main, src/assets
  server/   // new
  • Runtime: Node with Fastify. Small, fast, doesn't argue about TypeScript.
  • Database: Postgres. The save is a JSON document, but accounts, audit trail, and ladders are relational and you'll want real queries over them.
  • Sessions: an opaque refresh token in localStorage, short-lived access tokens on requests. No cookies, so the client stays a static bundle you can host anywhere.

Data model

account(id, created_at, email -- null until the player links one, email_verified)

credential(account_id, kind -- 'device' | 'email' | 'oauth', secret_hash, last_used_at)

character(
  id, account_id,
  world_seed,         -- currently the constant 20260812
  save jsonb,         -- exactly what serialize() produces
  save_version, content_hash,
  server_saved_at,    -- the server's clock, the only one that counts
  settled_at,         -- last time the ledger ran
  revision            -- increments on every accepted write
)

ledger_run(character_id, credited_seconds, kills, xp, gold, capped, created_at)

anomaly(character_id, tier, kind, observed jsonb, allowed jsonb, created_at)

The last two are the audit trail. You'll want ledger_run the first time someone reports lost progress, and anomaly is how you tune Tier 2 before it rejects anything.

API surface

Small on purpose. The client stays a simulation that occasionally syncs.

MethodPathPurpose
POST/v1/sessionCreate an anonymous account and character, or refresh a token. Returns the character and the offline report.
POST/v1/session/linkAttach an email or OAuth identity to an existing anonymous account.
GET/v1/characterFetch the save, with the ledger already settled against the server clock.
PUT/v1/characterUpload a save. Requires the revision you last read.
GET/v1/ladder/:metricRanked characters by level, kills, or apex clears. Phase 4.
GET/v1/world/bossesThe current window, and who has cleared each apex in it. Phase 4.
  • Every upload carries the revision you read. A stale revision means another device wrote first. Return 409 with the winning save and let the client re-hydrate. Never merge two saves — merging item bags silently duplicates gear.
  • The body cap is 64 KB. A legal save is bounded: 40 bag slots, 6 equipment slots, and a fixed set of id arrays. It can't legitimately grow past a few kilobytes.

The build order

Each phase ships on its own and is worth having even if the next one never lands.

0

Extract the shared package

Move the simulation and core into packages/sim and have the client import from it. No server, no behavior change. Do this first and alone — it's the only step that touches the whole tree, and doing it alongside a new server means every failure has two possible causes.

Done when npm run verify passes and nothing under packages/sim imports from packages/client.

1

Accounts and cloud saves

Anonymous account on first launch. storage.ts gains a remote implementation behind the same three functions it already exports, keeping the local save as a write-through cache — an idle game that white-screens on a dropped connection is worse than one with no server at all.

Done when you can level a character in one browser, open another, and continue it.

2

The ledger moves to the server

The server runs runOfflineLedger() against its own clock, applies the report, and returns it for the client to display. Remove the client-side call in the same change — two appliers means double credit, and double credit that only reproduces after a real absence is a miserable bug to find.

Done when setting your device clock forward a day earns you nothing.

3

Verification

Tier 1 as a rejection, Tier 2 as a shadow-mode record. Watch the anomaly table for a few weeks, tune the headroom, then decide whether Tier 2 rejects, clamps, or just flags an account.

Done when a save with hand-edited gear is rejected, and Tier 2's false-positive rate is low enough to act on.

4

The shared world

Ladders, an apex kill feed, and the one the ledger was written for — ghosts. You already know what another character killed last night and where, so you can show them doing it without simulating anything.

Done when the world feels inhabited without a single synchronized position.

Hazards

Each is cheap to handle now and expensive to discover later.

  • Double-credited offline time. Exactly one applier, always. Covered in Phase 2.
  • Item uid collisions. nextUid is a per-save counter. Two devices that diverge and later reconcile can hold two different items with the same uid — which is why Phase 1 needs revision-checked writes before there's anything to cheat.
  • Content drift. The decoder validates item bases, talents, and relics against the content tables. A server on a different build can reject a legal save, or pay out differently. Hash the tables at build time, store the hash with the save, and refuse to settle across a mismatch — ask the client to reload instead.
  • The world seed is a constant. Store it per character from day one anyway. Retrofitting it once players exist means a migration over live saves.
  • The 12-hour cap and lazy settling. Settling only on login is correct, but a ladder reading stored values shows absent players frozen. Project pending accrual at read time rather than ticking every character on a cron.
  • Sync failures must never interrupt play. Storage errors are already swallowed for this reason. The remote path needs the same discipline: a failed sync retries, it doesn't surface a modal.
