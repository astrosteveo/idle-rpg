Wildmarch · Technical plan

Server Backend Design

The server owns the simulation. The client sends input, draws what it's told, and decides nothing.

Repo astrosteveo/idle-rpg Branch worktree-server-backend-design Basis Two measurements, both reproducible in-repo

What authority buys, and what it costs

Buys: the save stops being a claim. Progress, loot, and elapsed time become facts the server produced. There is nothing to verify when the server rolled the dice itself. Ghosts, ladders, and a shared world stop being reporting features and become readouts of state the server already holds.

Costs: the simulation has to become something a server can host — a fixed timestep, randomness split by consequence, no dependency on the view, and a wire format separate from its internal state. Plus transport, session lifecycle, and client-side prediction so movement still feels immediate.

That's a real project. It's also almost entirely mechanical: the client already has an injected clock, an injected RNG factory, a command and event contract, a pure offline ledger, and a simulation that never touches the DOM. None of the rewrite requires re-architecting the game.

The trap this design avoids

Where projects like this die

“Server-authoritative” gets conflated with “deterministic lockstep.” Lockstep needs bit-identical results on both sides, which in JavaScript means fighting Math.sin, Math.cos, Math.atan2, and Math.pow — none specified to the last bit, all differing between V8, SpiderMonkey, and JavaScriptCore.

Wildmarch never needs determinism, and this plan is built so it never does. Three reasons, all specific to this game:

  • There is no shared space. Every player has their own world from one seed. No two clients ever need to agree on where a wolf is.
  • The client never decides anything. It doesn't roll damage, pick loot, or run AI. A slightly different number would have nowhere to go.
  • Combat is automatic. The player controls movement and two buttons. Nobody aims, so nobody notices 80 ms of latency on a wolf's approach.

So the client predicts its own movement only and interpolates everything else. That's a small shared module — terrain collision and position integration — not a bit-exact copy of the whole simulation.

What it costs to run

The load-bearing question for any authoritative design is whether you can afford to run the simulation for everyone at once. Measured with npm run bench, which runs the game headless with an injected clock — exactly as the server will.

Each run is ten simulated minutes of auto-battle that actually fights — 150 to 177 kills, level 9 to 11 by the end. Cost per tick is flat across rates because it's dominated by iterating roughly 120 beasts across 52 spawn nodes, so tick rate trades straight against capacity.

The decision this settles

20 Hz. Four times the fastest attack interval in the game, 0.74 ms of CPU per simulated second, an order of magnitude of headroom. Treat the figures as an upper bound — single-threaded, one machine, no network I/O or serialization. Budget a tenth of it and one eight-core box still carries a four-figure concurrent player count. Authority is affordable here, because Wildmarch's world is small, per-player, and resolved by rules rather than physics.

The architecture

One simulation instance per active session. No shared entity space, no interest management across players, no cross-session anything.

  │                                │

Three tiers of authority

An idle game can't keep a live simulation running for everyone forever — most players are away most of the time, and simulating an empty room is pure cost. Authority degrades in tiers, and the measurements above set the boundaries.

The gap between the ledger and the game

OFFLINE.efficiency is 0.72 and states the intent plainly: an hour away should be worth about 0.72 of an hour played, the discount covering healing, pathing, and waiting on respawns. Measured, it pays about half that, and the shortfall is stable.

Level 4, Greenwood Vale1,7878840.49×
Level 11, Greenwood Vale1,9179680.50×

Gold is worse and noisier — 0.16× to 0.27× — and experience worse still, though both are confounded: auto-battle roams by quest objective rather than by the assigned ground, so the live character drifts into richer regions and outlevels the one the ledger holds in place. The kills column is the trustworthy one, and 0.49 / 0.50 / 0.51 across three levels and two regions is too consistent to be roaming noise.

This is a live bug in the shipped game, not something the server introduces. It gets sharper under this design for two reasons:

  • The ledger becomes definitive. Today it's an estimate a client applies to itself. Afterwards it's the server's account of your night.
  • The tier boundary becomes visible. If catch-up pays full rate and the ledger pays half, the payout halves at the fifteen-minute mark. Players find cliffs like that in about a day, and the optimal play becomes reconnecting every fourteen minutes.

tests/unit/ledger-agreement.test.ts gates this. It's a characterization test: it asserts where the ratio sits today rather than where it should sit, because closing the gap is a balance decision — raise the ledger's rate, or accept a lower number as the real intent. Both sides are fully deterministic, so any movement in that test is a real change in the model. Fix it before Phase 3 ships, when the ledger stops being advisory.

The rewrite

Eight items, ordered by dependency, each independently reviewable.

R1

Fixed timestep

The simulation steps at exactly 20 Hz. The client accumulates real time into fixed steps and renders with the leftover as an interpolation factor. This deletes the quantise() median filter in main.ts — its sampling buffer and period estimation exist solely to stabilize a variable frame delta.

R2

Split the randomness by consequence

One stream currently serves both dice that matter and dice that don't. Damage variance, crit rolls, loot, rarity, AI transitions, wander points, and respawn jitter share a sequence with float-text offsets, corpse lean, effect angles, and spark positions.

Split into sim (outcome-changing, server-only, position saved so a session resumes mid-stream) and fx (only ever seen, client-only). Roughly 25 call sites, each a one-line classification. The most invasive item and the most mechanical — and once cosmetic draws stop perturbing the loot stream, the simulation becomes replayable for debugging.

R3

Take the view out of the simulation

setView() feeds the camera rectangle into the simulation, and exactly one rule reads it: shouldGiveUp(), which ends a chase when a beast is dragged off the visible screen. That's a fairness bug independent of any server — an ultrawide monitor currently gets longer chases than a phone. Replace it with a fixed leash in world units.

R4

Separate simulation state from wire state

Enemy has 35 fields, most of them server-side AI bookkeeping the client never draws. Serialized naively that's 582 bytes per beast, and a full snapshot of 122 beasts is 71 KB — 1.4 MB/s per player at 20 Hz.

Define an EnemyView of about twelve fields, quantized to roughly a dozen bytes, scoped to an interest radius, sent as deltas at 10 Hz. Thirty visible beasts then costs about 3.6 KB/s. The wire format is the real bottleneck in this design, not the simulation.

R5

Make the simulation host-agnostic

Mostly already true. What remains is removing the last assumptions that a renderer is present, and moving the simulation and core into a package both sides import.

R6

Transport and session lifecycle

WebSocket. The client sends batched input frames stamped with a sequence number; the server replies with snapshot deltas and the last sequence it processed. Session states are connecting, live, draining, hibernated.

R7

Client-side prediction, movement only

Extract position integration and terrain collision into a module both sides call. The client keeps a ring buffer of unacknowledged inputs and replays them when the server acknowledges a sequence with an authoritative position.

Abilities are optimistic: the button lights, the cooldown starts, the server confirms or rejects. Damage numbers appear only when the server says so — fine, because you aren't aiming.

R8

Reconcile the ledger with the simulation

The measured gap above. Listed here because it's a shipping requirement, not a nice-to-have.

What survives from the client-authoritative plan

  • readSave() stays. Still the decoder for anything arriving from outside — and under authority, the outside includes existing localStorage saves being imported.
  • verify.ts stays, retargeted. The server generates every item, so nothing needs verifying for anti-cheat. Two uses remain: validating imported saves at migration, and asserting internal invariants in tests, where it catches server bugs rather than cheaters. Its 19 tests keep earning their place.
  • The wall-clock apex schedule stays. bossWindow() needs no server to agree across clients, and now the server can record who turned up.
  • The data model stays, minus the anomaly table. Keep ledger_run for support questions.

The build order

Each phase ships alone and is worth having if the next never lands.

0

Extract the shared package

Move the simulation and core into packages/sim; the client imports from it. No server, no behavior change.

Done when npm run verify passes and nothing in packages/sim imports from the client.

1

Make the simulation hostable

R1 through R5, in order. Still no server — the game runs in the browser exactly as it does now, on a fixed timestep, with split randomness, no view dependency, and a wire type it doesn't yet use. This is the rewrite, and it lands with the game playable at every step.

Done when the browser game plays identically, npm run bench still reports its capacity, and the simulation compiles with no reference to window or a view rectangle.

2

The server runs the simulation

R6 and R7. Accounts, WebSocket sessions, one simulation per connection, prediction and interpolation on the client. No offline handling yet: disconnect ends the session and the character is saved where it stood.

Done when you can play a full session with the simulation on the server and movement still feels immediate.

3

Absence

Hibernation, the catch-up tier, and the ledger tier. R8 ships here or before.

Done when a fifteen-minute disconnect resumes exactly, a twelve-hour one settles through the ledger, and the payout at the boundary doesn't jump.

4

The shared world

Ladders, an apex kill feed, and ghosts — all readouts of state the server already holds.

Done when the world feels inhabited without a single synchronized position.

Hazards

  • The tier boundary. Catch-up and ledger must pay comparably or players will farm the seam.
  • Hibernation must be atomic. Serializing a character while a tick is in flight is how duplicated loot happens. Drain, then snapshot, then stop.
  • The RNG split is easy to get subtly wrong. A draw classified as cosmetic that actually feeds an AI decision reintroduces the dependency. Review R2 call site by call site, not file by file.
  • Interpolation and the 12-hour cap don't compose. A client watching an interpolated world after a rate-model settle will see beasts pop into place. Settle, then tick, then stream.
  • Content drift between client and server. Hash the content tables at build time and refuse a session across a mismatch. Under authority this matters more, not less: the client's renderer indexes into the same tables.
  • The world seed is a constant. Store it per character from day one anyway.
  • Prediction divergence on terrain. The predictor and the server must share collision code exactly, or players rubber-band at walls — the one place where a small numerical disagreement is visible.
